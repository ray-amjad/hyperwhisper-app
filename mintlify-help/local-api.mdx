---
title: Local API Server
description: Turn on the HyperWhisper HTTP server to control transcription from MCP clients, Shortcuts, Raycast, or a shell script.
---

HyperWhisper includes an optional HTTP server. The server listens on `127.0.0.1` only, and the network cannot reach it. When the server starts, it writes a discovery file with the port and a bearer token. MCP wrappers, benchmark scripts, and Shortcuts read this file. You do not copy the credentials anywhere.

The server is **off by default**. You turn it on one time in Settings. It stays on across restarts.

## Turn on the server

<Tabs>
  <Tab title="macOS">
    1. Open **Settings → API Server**.
    2. Set the toggle to **on**. The status line then shows the bound address and the last four characters of your bearer token.
  </Tab>
  <Tab title="Windows">
    1. Open **Settings → Local API**.
    2. Set the toggle to **on**. The status line then shows the bound address and the last four characters of your bearer token.
  </Tab>
  <Tab title="Linux">
    1. Open the main window, then click **Settings**. Scroll to the **Local API** section.
    2. Check **Enable the loopback-only local API**.
    3. Click **Save settings**. The status line then shows the result of the start.

    Linux shows the same fields as the other platforms in one list, not in tabs.
  </Tab>
</Tabs>

When the server runs, the panel shows three tabs on macOS and Windows: **Connection**, **MCP setup**, and **cURL**. Linux shows the same content as one list.

## Connection tab

The Connection tab shows the current values that you need to make requests to the server.

| Field | What it shows |
|---|---|
| **Port** | The port that the server listens on. The **Copy** button copies the port to the clipboard. |
| **Bearer token** | Hidden by default. Click **Reveal** to show the full value. Click **Copy** to copy the token. Click the regenerate button to make a new token (see the next section). |
| **Port file** | The full path of the discovery file. The **Show** button opens the file in Finder (macOS) or Explorer (Windows). Linux shows the path in a read-only field that you can copy. |

If an error occurs after the server starts (for example, the port is already in use), an orange warning appears below these fields.

### Bearer token

Every request except `GET /health` must include the bearer token:

```
Authorization: Bearer <token>
```

HyperWhisper makes the token the first time the server starts. macOS keeps the token in the Keychain. Windows keeps the token in a DPAPI-protected file at `%LOCALAPPDATA%\HyperWhisper\local-api-token.bin`. Linux keeps the token in an owner-only file at `$XDG_DATA_HOME/hyperwhisper/local-api-token`. The token stays the same across restarts. You do not update your scripts each time.

To make a new token, click the regenerate button. This button is a circular arrows icon on macOS, a rotate button on Windows, and a **Regenerate** button on Linux. The previous token stops immediately. Update each MCP client and each script that cached the old token. These clients and scripts can read the new value from the discovery file.

### Host and Origin check

The server also examines the `Host`, `Origin`, and `Sec-Fetch-Site` headers on each request. The server returns `403` for a request that is not a true loopback call. This check protects you against DNS-rebinding attacks from a browser tab. macOS, Windows, and Linux all make this check, and all three make it on every route, including the unauthenticated `GET /health`.

A request is a true loopback call when all three of these are true:

- `Host` is `127.0.0.1:<port>` or `localhost:<port>`, with the port that the server is bound to. A missing `Host` header is a rejection.
- `Origin` is absent, empty, or `http://127.0.0.1:<port>` or `http://localhost:<port>`. Any other value is a rejection.
- `Sec-Fetch-Site` is absent, `same-origin`, or `none`. A browser sends `cross-site` for a rebound request, and that is a rejection.

A command-line client sends the correct `Host` and no `Origin`, so it needs no change. Do not set your own `Host` header, and do not send an `Origin` header for a different site.

## MCP setup tab

The MCP setup tab shows the configuration to paste into your MCP client. The bridge reads the discovery file when it starts. Thus no port and no token appear in the client configuration.

```json
{
  "mcpServers": {
    "hyperwhisper": {
      "command": "npx",
      "args": ["-y", "@hyperwhisper/mcp"]
    }
  }
}
```

The **Copy** button copies the full block. For step-by-step instructions for Cursor, Claude Desktop, and Claude Code, read the [MCP setup guide](/api-reference/local-api/mcp-setup).

<Warning>
  The Linux app shows this same block, but the `@hyperwhisper/mcp` bridge does not read the Linux discovery file yet. The bridge looks for the macOS path on every platform that is not Windows, so on Linux it reports `HYPERWHISPER_NOT_RUNNING`. Until the bridge adds the Linux path, call the endpoints directly with the cURL snippet below.
</Warning>

## cURL tab

The cURL tab shows shell commands that contain your current port and token.

<Tabs>
  <Tab title="macOS">
    When the server runs, the snippet contains your current values:

    ```bash
    PORT=<your port>
    TOKEN=<your token>
    curl -s http://127.0.0.1:$PORT/health | jq .
    curl -s -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:$PORT/models" | jq .
    ```

    If the server does not run, the snippet reads the values from the discovery file:

    ```bash
    PORT=$(jq -r .port ~/Library/Application\ Support/HyperWhisper/local-api.json)
    TOKEN=$(jq -r .token ~/Library/Application\ Support/HyperWhisper/local-api.json)
    curl -s http://127.0.0.1:$PORT/health | jq .
    curl -s -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:$PORT/models" | jq .
    ```
  </Tab>
  <Tab title="Windows">
    When the server runs, the snippet contains your current values:

    ```powershell
    $PORT = <your port>
    $TOKEN = "<your token>"
    curl http://127.0.0.1:$PORT/health
    curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:$PORT/models
    ```

    If the server does not run, the snippet reads the values from the discovery file:

    ```powershell
    $discovery = Get-Content "$env:LOCALAPPDATA\HyperWhisper\local-api.json" | ConvertFrom-Json
    $PORT = $discovery.port
    $TOKEN = $discovery.token
    curl http://127.0.0.1:$PORT/health
    curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:$PORT/models
    ```
  </Tab>
  <Tab title="Linux">
    Linux always reads the values from the discovery file:

    ```bash
    DISCOVERY="${XDG_DATA_HOME:-$HOME/.local/share}/hyperwhisper/local-api.json"
    PORT="$(jq -r .port "$DISCOVERY")"
    TOKEN="$(jq -r .token "$DISCOVERY")"
    curl "http://127.0.0.1:$PORT/health"
    curl -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:$PORT/models"
    ```

    The snippet needs `jq`. Install it with `sudo apt install jq` if the command is not available.
  </Tab>
</Tabs>

## Discovery file

When the server starts, it writes a JSON file. MCP wrappers and scripts read the port and the token from this file. You do not put these values in your code.

<Tabs>
  <Tab title="macOS">
    ```
    ~/Library/Application Support/HyperWhisper/local-api.json
    ```

    HyperWhisper creates the file with `chmod 600`. Only your user account can read the file.
  </Tab>
  <Tab title="Windows">
    ```
    %LOCALAPPDATA%\HyperWhisper\local-api.json
    ```

    The NTFS ACL permits access from your Windows user account only. This is equivalent to `chmod 600`.
  </Tab>
  <Tab title="Linux">
    ```
    $XDG_DATA_HOME/hyperwhisper/local-api.json
    ```

    This is normally `~/.local/share/hyperwhisper/local-api.json`.

    HyperWhisper writes the file atomically, then checks that only your user account can read it. If the check fails, the server stops itself instead of leaving a readable token on disk. The status line then reports `local_api.discovery`.
  </Tab>
</Tabs>

The file has this structure:

```json
{
  "port": 39201,
  "pid": 12345,
  "started_at": "2026-06-02T13:57:46Z",
  "api_version": 1,
  "app_version": "2.36.0",
  "token": "9YH8r0Z1u3Xl..."
}
```

The server deletes the file when it stops correctly. If you force-quit HyperWhisper, the file can stay on disk until the next start. The next start writes new values over the old file.

<Note>
  If you see **Connection refused** and the discovery file is present, the file records an old port. Set the Local API switch to off, then set it to on again. The server writes a new file.
</Note>

## Port

The server has no fixed port. At the first start, it asks the operating system for a free port. It then keeps that port and uses the same port at each later start. Thus a script that holds the port in its code continues to operate across restarts.

If the kept port is not free at a later start, for example because a different program took it, the server does not fail. It asks the operating system for a new free port and writes the new port into the discovery file. To make a script that always finds the server, read the port from the discovery file.

<Note>
  Linux is different. It gives you a **Preferred port** box, and the default is `51671`. HyperWhisper tries that port first. If the port is taken, it asks the operating system for any free loopback port instead, and it writes the port that it really got into the discovery file. Set the box to `0` to always ask for a free port.

  The **Port** row below the box shows the port that the server actually bound, which can be different from your preferred port. Read the discovery file, not the box.
</Note>

## Request timeout

A `/transcribe` or a `/post-process` call is slow. A large local model, or a slow cloud model, needs 30 to 90 seconds, and sometimes more. On macOS, the server allows 10 minutes for one request. On Windows, the server sets no limit on the time of one request.

Set the timeout of your own HTTP client higher than its default value. Many clients apply a short default timeout. Such a client reports a failure while the transcription is still in progress.

## Available endpoints

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/health` | None | Server identity and status. |
| GET | `/models` | Required | Model catalog. |
| GET | `/modes` | Required | List saved Modes. |
| POST | `/modes` | Required | Create a Mode. |
| GET | `/modes/{id}` | Required | Fetch one Mode. |
| PATCH | `/modes/{id}` | Required | Partial-field update. |
| DELETE | `/modes/{id}` | Required | Delete a Mode. |
| POST | `/transcribe` | Required | Transcribe an audio file. If you give a `file` path instead of `audio_base64`, the path must be inside your recordings folder. The server rejects all other paths. |
| POST | `/post-process` | Required | Rewrite text with a preset prompt or a custom prompt. |
| GET | `/recordings/search` | Required | Substring search across past transcripts. |
| GET | `/recordings/{id}` | Required | Single transcript row. |
| GET | `/recordings` | Required | Windows only — undocumented alias for `/recordings/search`. |

The [OpenAPI reference](/api-reference/local-api/openapi.yaml) gives the full request and response schemas.

### What `/transcribe` does to the text

`/transcribe` does not run AI post-processing. `/post-process` is the endpoint for that. This is true even when the Mode you name has AI post-processing on.

The deterministic text steps are different. They are your own settings, and they contain no AI. On all three platforms, the `text` field gives you the transcript after these three steps:

- **[Vocabulary](/vocabulary) replacements.**
- **Dictated break commands.** "New line" and "new paragraph" become a line break in the text.
- **Remove filler words**, when that setting is on. This step applies to English only. "Er" and "um" are real words in other languages, so the step leaves every other language alone.

<Note>
  The `text` is not always identical to the text that dictation puts in your target application. Dictation of a Mode with AI post-processing on runs the AI rewrite, and this route never does. Dictation also applies insert-time steps that no API response can carry, such as Autocapitalize Insert and the trailing space.
</Note>

<Warning>
  Each platform decides "is this English?" the way its own dictation does, so one case differs. Windows and Linux read the language of the request or the Mode. The default is `auto`, which is not English, so they do not remove filler words — send `"language": "en"` to make the step apply. macOS prefers the language the engine reported for the transcript, and falls back to the request's language when the engine reported none. So a `"language": "auto"` request against an engine that reports English does remove filler words on macOS and not on the other two. The other two steps behave the same everywhere.
</Warning>

### When `mode_id` and `engine` disagree

You can send `mode_id` and `engine` in the same `/transcribe` request. The Mode is the baseline, and the `engine` replaces the provider for this one call. The two can name different cloud vendors, and then the question is which model runs.

The Mode's saved model does **not** move to the other vendor. Each platform drops it and uses the engine's own default model. A model id is not portable between vendors: `nova-3-general` is a Deepgram model, and an OpenAI request that carries it is rejected — or, worse, is accepted because the same text is also a model of that vendor, and you are billed for a model you did not ask for.

Three rules follow:

- **An explicit `model` wins.** Send `"model"` to pin one. For a BYOK provider the value goes to the vendor as you sent it, and no other rule applies.
- **A model that really belongs to the engine you named is kept.** This includes an old name for a current model. An AssemblyAI Mode saved with `universal`, re-run with `"engine": "assemblyai"`, still runs `universal`. It is not silently changed to a different model at a different rate.
- **HyperWhisper Cloud is different.** It selects the model from the Mode's accuracy tier, not from a model id. `"engine": "cloud"` keeps the Mode's model only when that model is one of the tier's models, and uses the tier's default model in every other case. This applies to an explicit `model` too.

Read the response `model` field to see which rule applied. It names the model that ran. It is empty only for an engine that takes no model parameter, which the [OpenAPI reference](/api-reference/local-api/openapi.yaml) describes in full.

<Note>
  Two engine names behave differently on Linux: `googlespeech` and `microsoftazurespeech`. These are old names for providers that Windows and macOS now serve through HyperWhisper Cloud, so those two platforms spend HyperWhisper Cloud credits. Linux still treats them as your own API key. Name the provider you want directly — `cloud` for HyperWhisper Cloud — until this is made the same everywhere.
</Note>

### Mode write rules

`POST /modes` and `PATCH /modes/{id}` reject an empty mode name and a case-insensitive duplicate. Windows trims whitespace at the start and end of the name. macOS also normalizes Unicode and trims invisible-only characters from the boundaries. A macOS name must contain at least one visible base character.

Exactly one Mode is the default Mode, and its name is fixed. Two rules follow, and all three platforms apply them:

- A `PATCH` that changes the name of the default Mode returns `ok: false` with `INVALID_REQUEST`. The name field is disabled in the app for the same reason. Rename a different Mode, or make a different Mode the default first.
- `"isDefault": true` moves the flag. The Mode that held it stops being the default in the same request. `"isDefault": false` on the only default Mode returns `ok: false` with `INVALID_REQUEST`, because it would leave no default Mode.

`DELETE /modes/{id}` on the default Mode moves the flag to the first remaining Mode. A restored backup that carries two default Modes, or none, is repaired the same way when the app starts.

On macOS, `postProcessingMode` must be `0`, `1`, or `2` on create and patch. A PATCH `sortOrder` must be from `-32768` to `32767`. macOS ignores `sortOrder` on create and assigns the next stored order. An invalid value returns `ok: false` with `INVALID_REQUEST` and does not change the mode.

For a macOS PATCH, an omitted field stays unchanged. An explicit JSON `null` clears these string fields: `customInstructions`, `userSystemPrompt`, `languageModel`, `cloudTranscriptionModel`, `cloudTranscriptionDomain`, `cloudProvider`, `postProcessingProvider`, `englishSpelling`, `cloudAccuracyTier`, `geminiCustomPrompt`, and `cloudPostProcessingModel`. Windows treats `null` like an omitted value for these PATCH fields.

<Note>
  The two platforms are different in two ways. On macOS, `GET /models` accepts the `?kind=` and `?installed_only=` query parameters to filter the catalog. Windows ignores these parameters and always returns the full catalog.

  Windows accepts and returns five more mode fields than macOS: `localEngine`, `localParakeetModel`, `localPostProcessingModel`, `customVocabulary`, and `providerType`. These fields hold the Windows settings that have no macOS equivalent. macOS ignores these keys when you send them, and never returns them.
</Note>

The `providers` array includes `key_present`, `reachable`, and `status`. A Meta key reports `status: "configured"` and `reachable: false`. Meta has no safe empty request for key validation. A transcription validates the key for that request, but the health endpoint stays conservative. macOS and Windows use the same status.
